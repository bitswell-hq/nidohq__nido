## T-sdk-F1 — decompileRules shows a spending-limit-only multi-signer rule as N-of-N 'all' although OZ lets any one signer authorize it

- Source: T-sdk (finding)
- Jev improves: 0.92
- Jev defect / severity: requirement_or_code / medium
- Locations: nido/packages/passkey-sdk/src/policyDoc/decompile.ts:36-49, nido/packages/passkey-sdk/src/policyDoc/decompile.ts:100-131

decompileRules always emits principals {type:'all', signers: <every chain signer>} for a mappable rule. That is only true when the chain rule has NO policies (OZ get_validated_context_by_id checks all signers only when policies.is_empty()) or when the interpreter's MinSigners(N) re-imposes the floor. A chain rule carrying only the spending-limit policy (no interpreter) is accepted by mapRule: the spending-limit branch sets cap and nothing checks the signer floor. OZ spending_limit::enforce only requires a non-empty authenticated signer set, so on chain any ONE of the N signers can spend up to the cap. The decompiled view claims all N must sign, and the assembled doc, re-lowered, yields MinSigners(N). A second instance from the same root cause (mapRule never checks the scope a cap may take): a capped chain rule scoped to CallContract(account) decompiles to {scope:self-admin, cap:...}. perch_ir::validate refuses that combination (CapWithoutToken), and lowerDoc throws on it, yet decompileRules still returns it as a doc view with a docHash.

**Recommendation:** In mapRule, when the rule has policies but no interpreter program, the doc view must reflect the policies' quorum. Fall back to raw for chain.signers.length > 1 (or map to {type:'threshold', m:1} when the only policy is spending-limit). More generally, emit 'all' only when policies is empty or a decoded MinSigners equals the signer count.
