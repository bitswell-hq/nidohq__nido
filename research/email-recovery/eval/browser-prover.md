# Proving a recovery email in the browser

The wallet proves the recovery circuit (`circuits/email-recovery/recovery`,
2^18 UltraHonk gates) in the user's browser with `RecoveryProver` from
`packages/email-recovery`: a Web Worker running noir_js 1.0.0-beta.9 for the
witness and Barretenberg 0.87.0 (bb.js) for the zero-knowledge proof, with
Barretenberg threads when the page is cross-origin isolated
(`docs/email-recovery/spec.md` §6.5, §12).

**No phone was measured.** Every figure below comes from a desktop computer.
The rows are labelled with what they are:

- **Desktop**: Chrome on the machine named below.
- **Desktop, DevTools CPU throttling**: the same, under Chrome DevTools'
  `Emulation.setCPUThrottlingRate` (`chrome-devtools-axi emulate --cpu 4` or
  `6`). Chrome applies that throttling to the page only. Asked to throttle the
  prover's workers, it answers "Operation is only supported for pages, not
  workers" (Chrome 151), and bb.js always proves in workers of its own. These
  rows therefore show proving at desktop speed, and the main-thread probe
  column (a fixed loop timed on the page) shows the page itself was slowed.
  They are not a phone approximation.
- **Desktop efficiency cores**: a second Chrome started under macOS's
  background QoS clamp (`taskpolicy -c background`), which runs its threads
  on the efficiency cores only. This is a desktop's efficiency cores, a
  slower class of core than its performance cores, and not a phone.

## How it is measured

`measure-browser.mjs` builds nothing itself: it serves the built frontend
(`npx astro build --root packages/frontend`) with `tests/support/server.mjs`,
which sends the headers of `packages/frontend/public/_headers`, so the page is
cross-origin isolated exactly as the recovery routes are. It drives Chrome
for Testing through `chrome-devtools-axi` on the wallet's benchmark page,
`/security/recover/bench/`. That page proves the Gmail fixture
(`crates/integration-tests/fixtures/email/provider-gmail-com`, a TEST-ONLY
email signed by the provider mock's test key) with the same prover the
recover page uses, checks the proof's public inputs against the fixture's,
and verifies the proof against the verification key the on-chain verifier
embeds before reporting it.

| Column | Meaning |
| --- | --- |
| Proving | Barretenberg's `acir_prove_ultra_keccak_zk_honk` in the worker |
| Witness | The encoder's checks of the email and noir_js solving the circuit |
| Total | From the page's request to the verified proof, including the cached asset reads, Barretenberg's start, and the local verification |
| Cold total | The same with the prover's Cache API cache emptied first, so it includes the download |
| Barretenberg memory | Barretenberg's wasm linear memory after proving; it never shrinks, so this is its peak |
| Peak renderer RSS | The largest resident set size among the browser's renderer processes, sampled with `ps` every 200 ms during the configuration; the page, the prover's worker and Barretenberg's workers all run in the page's renderer |
| Main-thread probe | 50 million iterations of a loop on the page's main thread, timed by the page |

The download is the circuit artifact (2,011,102 octets), its verification
key (1,760) and the prefix of Barretenberg's CRS the circuit needs (16,777,280
octets of G1 points and the 128-octet G2 point), 18,790,270 octets in all,
fetched once and kept in the Cache API; the CRS is checked against pinned
SHA-256 digests. The prover's own code (the worker, bb.js with its
Barretenberg wasm, noir_js with its wasm) is part of the page's build and is
not counted there.

## On a phone

The benchmark page needs no account and no wallet state. Open
`/security/recover/bench/` on the recovery origin (any Nido subdomain, or a
build served with the recovery routes' headers), choose "Run with 1 thread"
or "Run with every core", and copy the JSON it prints. On a phone the page
reports whether it is cross-origin isolated and how many logical cores it
sees. Figures from real phones are not in this repository.
