# Measurements

Figures for the recovery circuit (spec §6) and the components it is built
from.

**How they are produced.** `scripts/measure.sh` installs and checks Perch's
pinned toolchain, compiles every package, and runs `scripts/measure.py`,
which rewrites the block below:

- gates: `bb gates -s ultra_honk` on each bench package's compiled ACIR.
  "Padded size" is the power of two the prover rounds the circuit up to,
  which sets proving time and the CRS a prover downloads;
- proving: `nargo execute` (witness generation) and
  `bb prove --scheme ultra_honk --oracle_hash keccak --zk`, the
  zero-knowledge flavor Perch's verifier accepts, on the inputs in each
  package's `Prover.toml`: for the recovery circuit, the Gmail recovery
  email of `crates/integration-tests/fixtures/email/provider-gmail-com`
  (`just gen-email-proofs` writes it); for the bench packages, what the
  test-vector generator writes (the Gmail-shaped header and its body where a
  package takes them). Every proof is checked with `bb verify --zk`. Times
  are medians of wall-clock time; memory is the largest peak resident set
  size of `bb prove`;
- bb.js: `packages/email-recovery/scripts/measure-bbjs.mjs` re-encodes the
  same fixture from its `.eml`, solves the witness with noir_js
  1.0.0-beta.9, and proves with bb.js 0.87.0 (`keccakZK`) in Node, with one
  worker thread and with one per core; memory is the Node process's peak
  resident set size, workers included. Its proof verifies under the
  verifier's key (the committed `proof.bbjs` of that fixture).

**The machine is shared** with other workloads (its load average is
recorded in the block). Times on it are upper bounds for an idle machine of
the same kind; gate counts do not depend on load. Phone-class figures, and
bb.js in a browser rather than Node, are not measured here.

## Reading the figures

- `header_parse_1024` is the cost of every header check without SHA-256 or
  RSA. Its rows above (`header_scan_1024`, `header_from_1024`,
  `header_tags_1024`) are cumulative, so the difference between consecutive
  rows is the cost of the From parser, the DKIM-Signature tag checks and the
  Subject parser.
- `dkim_header_1024` is everything a header-only DKIM proof needs at
  1024-byte headers: the checks of `header_sha_1024`, `rsa_2048` and
  `header_parse_1024` plus the key hash and output packing. Its gate count
  is below the sum of those rows because lookup and range tables are built
  once per circuit.
- `bench/recovery_1024` is `dkim_header_1024` plus the P2 hashes of
  `spec_hashes` (commitment, Subject opening, registry leaf and Merkle path):
  3,663 gates more. `recovery` is the same relation at the spec's 1536-byte
  header bound: about a third more gates, the same padded size 2^18, so the
  same verification key size and the same on-chain verification cost; the
  native and bb.js rows show what the larger bound costs the prover.
- bb.js on one thread is the setting of a browser without cross-origin
  isolation; with it, bb.js runs one worker per core.
- Every proof is 16,224 bytes, the size of the zero-knowledge UltraHonk
  proofs Perch's adapter accepts, whatever the circuit size.
- The body hash grows by one SHA-256 compression per 64 bytes of bound;
  the recovery proof does not use it (spec §4.4).
